# 包懂你｜AI 背包导购助手产品说明书

适用：赛夫集团 AI 能力测评 · A 赛道（技术向）
版本：V1.1（按当前网页功能核对）
更新日期：2026年10月31日
演示地址：https://baodongni.onrender.com

## 1. 产品概述

“包懂你”是一款面向背包购买场景的问答式 AI 导购助手。用户可以从模糊需求出发，通过多轮交流获得选款建议，也可以选择具体商品进行分析，或比较两至三款商品。

产品围绕“理解需求—筛选商品—说明取舍—辅助决策”构建最小可用闭环。AI 负责理解口语和生成解释，程序负责条件校验、商品绑定、比较表及追问规则。

本项目选择 A 赛道，交付可运行网页 Demo 与本产品说明书。网页通过 Python 后端调用真实 DeepSeek API；并非只有固定回复的界面演示。当前网页使用模拟／演示商品数据：部分名称、价格和销量参考截图，其余规格与图片用于演示。真实业务使用必须接入公司自身的商品与业务数据库，不能直接将演示资料作为真实销售依据。

## 2. 背景、用户与目标

背包选择涉及用途、预算、重量、容量、电脑适配、风格和背负体验。消费者往往只会说“夏天背、轻一点”“适合大学生、简约一些”，难以直接转化为完整参数。

直接搜索会产生大量相似结果，而商品标题、营销卖点和评论口径不一致，使比较困难。

目标用户包括：需求模糊的初次选购者、已有候选但不了解优劣的消费者，以及需要在多款商品间做取舍的用户。主要覆盖校园、日常通勤、休闲和短途出行，不提供专业登山或医疗护脊效果保证。

产品目标：降低表达成本；将模糊需求转成可执行条件；提供有差异的选择；解释适合与不适合之处；让文字说明与商品入口对应。

## 3. 功能范围

| 功能 | 用户操作 | 输出 |
| --- | --- | --- |
| 选品推荐 | 描述需求并补充条件 | 符合条件的主推、备选、优劣说明及必要追问 |
| 商品分析 | 选择卡片或提出单品问题 | 基本信息、优势、不足、评价资料及局限 |
| 商品比较 | 选择2—3款并确认 | 关键差异、比较表、适用场景及对应商品入口 |
| 多轮对话 | 补充用途、预算等信息 | 结合已了解的需求更新回答 |
| 猜你想问 | 点击相关问题 | 发起下一轮交流，过滤重复问法 |
| 历史记录 | 重进页面、选择历史或新对话 | 当前浏览器中的记录恢复或重新开始 |

聊天框内提供“选品推荐／分析商品／比较商品”切换。用户消息采用消费者表达，例如“请分析商品『某款背包』”，不展示商品ID或内部行为约束。

语音和图片入口已移除，首版聚焦稳定的文字导购。

## 4. 核心使用流程

### 4.1 选品推荐

用户描述需求后，系统提取意图与条件，校验资料库，优先提供3—5款主推，再展示其他备选。每款都说明优势和局限，避免把同款不同规格当作多样选择。

满足全部条件的商品不足3款时，按实际数量展示，不放宽要求凑数。参数缺失的候选单独归为待核实，不混称完全符合。

主推并非销量最高的固定商品，而是在当前需求下优先匹配，再参考有来源的销量、口碑资料和款式差异。缺少好评率时不声称“高好评”。

备选折叠展示，“查看全部符合条件的商品”支持继续浏览。

### 4.2 商品分析

一次回答基本信息、适用场景、优势、不足及评价资料是否充分。没有评论样本时说明缺失，不生成虚构买家原话。

同一商品的说明文字、卡片、参数和入口通过内部ID绑定。已提供准确详情链接时直达对应页面；缺少SKU时明确标注同名搜索，不能保证搜索结果是截图同款。

单品分析不追加需求追问。

### 4.3 商品比较

选择窗口呈现图片、商品名、参数摘要和商品入口，支持选择2—3款。

系统生成客观参数表，再由AI解释重量、容量、电脑适配、风格和主要局限的取舍。表头及商品说明均提供对应入口。

比较结论结合既有需求，不笼统宣称某款“全面更好”，也不追加追问。

## 5. 对“提示思考”的逐项回应

### 5.1 如何把用户原始模糊需求转化为核心诉求？

采用“明确表达—可能含义—待确认信息”三层拆解。

例如“想买个适合夏天、轻一点的双肩包”：明确的是双肩包、夏季使用、轻便；可能关注的是空包重量、背部闷热或外观轻盈；尚缺的是用途、预算、装载物品及背负时长。

系统不把推测直接当成事实。“夏天”不能自动等于透气，“女生”不能自动等于粉色或小容量。

核心诉求由使用场景、约束和偏好共同构成。例如用户补充“大学上课、200元内、带14英寸电脑”，可归纳为校园日常、预算受限、电脑携带、轻装偏好的组合，而不是只匹配“学生背包”关键词。

### 5.2 如何把口语化需求变成结构化属性和筛选条件？

DeepSeek 将自然语言转换成结构化条件变更，程序校验字段、类型和取值，再合并到保留条件。

| 用户表达 | 结构化处理 | 边界 |
| --- | --- | --- |
| “大学上课用” | 场景=校园 | 不推断所有大学生需求相同 |
| “200元以内” | 预算上限=200 | 超预算不算完全匹配 |
| “14英寸电脑” | 电脑标称适配不低于14 | 购买时仍需核对实际内尺寸 |
| “轻一点” | 可暂按包重不超过600g筛选 | 是首版规则，不是舒适度实测结论 |
| “简约、不要太花” | 风格=简约 | 不能仅凭性别代替风格判断 |
| “至少25L” | 容量下限=25 | 容量不能替代实际开口与尺寸 |
| “下雨不担心” | 关注防泼水 | 不解释为完全防水 |

需求按硬性条件、偏好和未知信息处理。硬性条件用于过滤；偏好用于排序和解释；未知值保持未知。演示参数会标明，不能作为真实购买保证。

保留条件由程序再次校验，AI不能仅凭描述把不匹配的商品推到主推。需求在后台记录，页面不展示技术化条件标签。用户通过对话补充用途、预算和携带物品等信息。

### 5.3 如何设计多轮对话，追问和澄清歧义？

采用“先给初步方向，再问一个关键问题”。已有信息足够时先展示候选，不要求填写完整问卷。

追问优先顺序：用途、预算、携带电脑时的尺寸、轻便／收纳／保护等优先偏好。每轮最多一个，放在整条推荐回答最后高亮，并提供快捷选项。

追问字段、已问字段和跳过字段由程序记录。已知、问过或明确不想回答的问题不机械重复。条件充分时不为维持聊天而强行追问。

只有选品推荐可以追问；分析、比较直接回答。模型正文不主动追加问题，程序统一控制追问位置与类型。

卡片操作通过内部ID确定目标，降低“第二款”“这款”指错商品的风险。纯文本同时涉及多款时仍有歧义风险，明确点击卡片是当前更可靠的操作路径，复杂指代消解仍可改进。

示例：用户“夏天背，轻一点”→给初步方向并询问用途；用户“大学上课”→保留轻便，补充校园场景并问预算；用户“200内，带14英寸电脑”→同时应用条件并更新候选；用户“第二款有什么缺点”→转为单品分析，不再追问用途。

### 5.4 哪些情况AI可能答错、幻觉或推荐不准，如何处理？

| 风险 | 处理 |
| --- | --- |
| 错解轻便、简约等表达 | 保留明确需求；推测不当事实，可通过后续表达纠正 |
| 性别等刻板推断 | 不由女生推断颜色、容量、预算 |
| 编造商品或优惠 | 仅引用资料库；商品ID须在库中存在 |
| 参数缺失仍称完全匹配 | 区分匹配与待核实候选，不混入主推 |
| 条件冲突或无匹配 | 说明局限，不擅自放宽，不凑推荐数量 |
| 文字与商品入口不一致 | 用同一内部ID绑定说明、参数、卡片与链接 |
| 编造好评率和买家评论 | 无来源字段不填，不生成虚假评论原话 |
| 搜索入口冒充详情 | 准确SKU链接与同名搜索分开标注 |
| JSON无效导致整轮失败 | 仅需求提取使用短JSON，支持解析与一次结构修复 |
| 分析、比较因JSON失败 | 正文使用普通文本，比较表由程序生成 |
| 空正文、截断或暂时连接失败 | 有限重试、明确错误和可重试入口；不伪造成功回答 |
| 未获得正文只有推理内容 | 不把内部推理内容作为用户答案展示 |

这些措施降低风险，不代表错误率为零。真实商品数据、网络和模型服务仍影响最终效果。

## 6. AI与程序分工

推荐链路：用户输入→意图与条件提取→字段校验→合并需求→资料筛选→排序与去重→回答生成→按商品绑定文字与入口→必要追问。

明确选中商品的分析与比较可以直接进入回答生成，减少不必要的提取调用。

模型负责语义、语气、解释与上下文理解。程序负责条件过滤、数据边界、商品绑定、比较表、追问控制和结果校验。当前不宣称使用知识库检索系统、模型微调或全网自主搜索。

Prompt分为两层：提取Prompt要求只返回本轮条件变化，不重复填回已取消条件；回答Prompt要求只根据提供资料说明优劣，不编造口碑、优惠或链接，不展示内部ID与指令，不在非推荐场景追问。

## 7. 模拟数据、真实数据库与使用边界

### 7.1 当前网页：真实AI调用，模拟商品数据

当前版本通过真实DeepSeek API理解与生成回答，但网页商品数据属于模拟／演示数据，不等于已经接入真实电商数据库。

资料库包含22个不同商品家族。前六款名称、截图参考价格及可见销量参考用户提供的京东列表截图，其余用于补充演示款式。为展示筛选与比较而补充的容量、尺寸、面料等为演示参数；主图为AI生成的写实款式示意，并非对应商家实拍。

截图没有提供的好评率、完整评论、准确SKU链接不作真实推断。没有可靠评论样本时，单品分析说明评价依据不足，不生成虚构消费者原话。

因此，“能回答问题、能展示选款流程”不等于“已能对真实在售商品作可靠购买推荐”。当前不保证实时价格、库存、活动资格、商品真伪，也不提供交易能力。

### 7.2 正式使用：接入公司自身数据库与授权接口

真实业务应将演示资料替换为公司自身的商品主数据和授权业务数据，通过受控后端接口读取，不让模型直接访问数据库或执行SQL。

| 数据来源 | 需要接入的内容 | 用途 |
| --- | --- | --- |
| 商品主库／PIM | 商品ID、SKU、品牌、标题、规格、主图、状态 | 确保描述、参数、图片对应同一商品 |
| 商城／OMS／库存系统 | 在售价格、库存、上下架、可售地区 | 防止推荐无货或已下架商品 |
| 店铺与交易数据 | 有明确统计周期的销量、店铺及商品详情链接 | 支撑真实商品入口和销量信息 |
| 评论与售后数据 | 脱敏评论、评价时间、好评率口径、常见问题 | 支撑优劣总结与风险提示 |

具体系统名称按公司现有架构确定；若公司已有统一商品中心，可优先复用其接口。当前本地商品资料文件只是原型扩展入口，不能替代正式数据库接入。

推荐流程应为：聊天需求结构化→公司商品接口检索→校验SKU、价格和库存→获取必要评论摘要→AI解释推荐→绑定公司真实商品详情链接。

上线前还需设置字段口径、更新时间、访问权限和数据脱敏。不同平台、不同规格、不同时间周期的销量和好评率不能直接混为同一口径；缺失信息继续保持未知。

## 8. 页面与技术实现

前端使用HTML、CSS和JavaScript；后端使用Python，通过服务端调用DeepSeek接口。GitHub保存代码，Render运行网页与后端并提供HTTPS地址。

密钥配置在服务端环境变量，不写入网页或公开仓库。浏览器记录使用本地存储，不自动跨设备同步，也不构成电商账户登录。文字聊天和必要资料会发送到配置的模型服务。

当前通过最近若干条对话与持续保留的结构化需求维持上下文，不把全部历史无限发送给模型。

## 9. Token、费用与开放管理

打开网页并不等于调用AI。打开页面、刷新、看商品资料、打开商品链接和勾选比较项，不触发模型请求。

发送消息、点击分析、确认比较或点击“猜你想问”会调用AI，消耗输入与输出Token。输入包含系统说明、必要商品资料、近期历史和本轮问题；输出包含结构化条件或回答文字。

| 操作 | 典型调用情况 |
| --- | --- |
| 打开、刷新、浏览、勾选 | 0次模型调用 |
| 自然语言选品 | 通常1次需求提取＋1次正文生成 |
| 明确选中商品的分析／比较 | 通常1次正文生成 |
| 其他自然语言问题 | 视意图识别与正文生成路径而定 |
| 格式修复、空回复或连接重试 | 可能增加调用和消耗 |

实际费用以DeepSeek当前计费规则与控制台记录为准，不能把一次点击固定换算为一个费用。没有向用户展示回答，也不保证该请求没有消耗额度。

若线上服务共用作者密钥，所有访客的AI调用计入作者账户；评委无需提供密钥。免费Render托管不代表免费模型调用。

当前已通过限制历史、缩小必要资料、分析比较跳过重复提取及限制重试次数控制开销。访问认证、每人次数、每日费用上限等尚未实现，公开长期运营前应补充。

评测期间可保持链接开放；评审结束后可暂停或删除Render服务，保留GitHub代码、视频和说明书。共享给其他项目的密钥无需一并删除。

## 10. 验证与建议演示

已进行浏览器交互、移动端布局、聊天恢复、商品绑定、比较表、重复问题过滤、JSON异常、空回复和重试分支等测试。部分异常测试使用受控模型响应，不等同真实服务稳定性或商业效果验收；不提供未经统计的准确率、转化率或可用性承诺。

建议演示：

1. 输入“想买适合大学生的简约背包，女生”。检查核心诉求及有差异候选。
2. 补充“200元以内，带14英寸电脑”。检查需求保留与重新筛选。
3. 点击某款分析。检查基本信息、优势、不足及对应入口，不追问。
4. 在聊天框查看并切换“选品推荐／分析商品／比较商品”任务入口，确认操作入口和消费者语言提示与页面一致。
5. 查看回答中的商品卡片和商品入口，检查名称与说明是否对应，并区分准确详情链接和同名搜索入口。
6. 刷新页面或开启新对话。检查历史保留与需求重置。

提交前应确认Render部署最新代码、密钥和额度有效，并在真实演示链接完成一次完整流程。免费实例闲置后首次唤醒可能较慢，不应把首次加载速度直接当作模型响应速度。

## 11. 后续迭代计划

以下为计划能力，不表示当前网页已经实现。

| 方向 | 计划内容 | 前置条件与验证重点 |
| --- | --- | --- |
| 真实商品数据库接入 | 替换模拟商品与演示规格，使用公司真实SKU、主图、价格、库存和链接 | 授权接口、字段一致性、数据更新与权限控制 |
| 语音输入 | 用户口述需求，转写后允许修改，再发送聊天 | 麦克风权限、HTTPS、语音服务可用性与额外费用；保留文字输入兜底 |
| 图片上传与识别 | 上传背包图或商品截图，提取可见特征并定位候选商品 | 视觉模型与公司商品图库；不能只靠颜色认定同款，需允许用户确认 |
| 评论与售后分析 | 基于真实、脱敏样本总结好评点、争议和常见不足 | 样本量、规格与时间口径明确，避免把少量评论当整体结论 |
| 复杂需求理解 | 改善多商品指代、需求冲突及多轮偏好变化 | 建立真实表达测试集，评估条件遵守和目标绑定 |
| 成本与访问管理 | 增加认证、调用频率限制、预算上限与使用统计 | 明确密钥归属、额度、报警和停服策略 |

语音与图片功能当前没有保留入口。后续接入时应先明确用户授权、文件处理范围、服务商及数据保留方式，再提供交互，避免出现按钮存在但能力不可用的情况。

当前交付重点是展示模糊需求理解、多轮推荐与可解释选择的闭环。正式商业使用需要以真实公司数据、持续测试和运行治理为基础。
